# L2 — системный дизайн предпроцессинга транзакций

Репозиторий без кода: одно задание по проектированию слоя предпроцессинга (POS → Processing).
Результат работы — документ с проектными решениями, а не программа. Не искать здесь сборку,
тесты и зависимости, их нет.

## Вход

- `system_design_task` — полное ТЗ: сценарии, функциональные и нефункциональные требования,
  ограничения, перечень ожидаемых артефактов. Источник истины по условиям.
- `system_design_image.png` — предложенный шаблон архитектуры.

## Правила работы

- Условия ТЗ не додумывать. Нет данных для решения — относить в «Список уточняющих вопросов»
  (артефакт 1), а не выбирать молча.
- Раздел «Ожидаемые артефакты» из ТЗ — чеклист полноты. Готовым считать только тогда, когда
  закрыты все 10 пунктов; что не закрыто — называть прямо.
- Числам из ТЗ не противоречить: 5 000–20 000 TPS, p95 < 100–200 мс на путь до отправки в
  процессинг, SLA 99.99%, active-active, AP с eventual consistency. Capacity planning давать
  расчётом с явными допущениями (размер сообщения, репликация, запас на burst), а не оценкой
  «на глаз».
- Границы из ТЗ считать заданными: нет strongly-consistent глобального хранилища, ответы от
  процессинга приходят асинхронно и по другому соединению, POS повторяет запросы.
- Схема архитектуры — C4 в mermaid. Исходник диаграммы держать в репозитории текстом рядом с
  документом, а не только картинкой: mermaid входит в diff, png не входит.
- Состояния транзакции описывать машиной состояний с переходами для retry, двухфазной операции
  и реверса; идемпотентность ключом запроса, повторные реверсы — отдельным случаем.
- В анализе точек отказа для каждого отказа указывать наблюдаемый симптом и как деградирует
  система, а не только «нужен retry».
