## 1. «Хвост меньше 1 с восстанавливается сверкой с процессингом» — как это происходит?

**Что такое хвост.** Стендин получает данные блока асинхронно, с отставанием до 1 с. Если
блок упал целиком, в стендине нет операций последней секунды: при 3 300 TPS это до ~3 300
строк. Операция при этом могла уже уйти в процессинг.

**Пока идёт сверка, терминалы `91 HOLD` не получают.** Отказ `91 HOLD` терминалы блока получают только
во время самого переключения (30–40 с). После него блок в стендине работает как обычно, а
сверка идёт в фоне.

Сверка — это не одно приложение, а три механизма. Первые два работают сами, третий
запускается по регламенту аварии.

| # | Кто | Когда | Что делает | Что спрашивает у процессинга |
|---|---|---|---|---|
| 1 | Transaction Receiver в стендине, «окно потерь» — до конца сверки (уточнено: ответ 5 второго раунда) | Пришёл повтор (`0201`) или реверс (`0400`), а исходной операции в базе нет | Не считает операцию новой. Вычисляет `operationId` из полей сообщения (он детерминирован) и спрашивает процессинг | `POST /v1/status`. Процессинг знает операцию — берём его статус и восстанавливаем строку. Не знает — обрабатываем как новую |
| 2 | Timeout Monitor в стендине | Сразу после переключения | Проходит все незакрытые операции блока, которые в стендин попали, и выясняет их судьбу | `POST /v1/status` пачками по 100, в пределах бюджета (≤ 5 % лимита) |
| 3 | Разовый запуск сверки по регламенту (Kubernetes Job `reconcile`, тот же образ; подробно — ответ 4 второго раунда) | Когда старый primary снова доступен, до его пересоздания | Читает из старого primary строки за окно аварии, которых нет в стендине, и по каждой принимает решение (таблица ниже) | `POST /v1/status`, при необходимости `POST /v1/reverse` |

**Решение по каждой потерянной строке (механизм 3)**

| В старом primary | У процессинга | Что делаем |
|---|---|---|
| Ответ терминалу доставлен, одобрено | `APPROVED` | Восстанавливаем строку в стендине. Клиент получил чек, деньги списаны — всё сходится |
| Ответ не доставлен | `APPROVED` или `IN_PROGRESS` | Реверс. Терминал ответа не видел и считает операцию неуспешной |
| Любое | `REVERSED` | Терминал уже сам отменил операцию (см. ниже). Восстанавливаем строку как отменённую |
| Любое | `NOT_FOUND` | До процессинга не дошла. Ничего не делаем |
| Данные противоречат друг другу | — | Ручной разбор, запись в аудит |

**Почему большинство случаев закрывается без третьего механизма.** Терминал, не получивший
ответ за 30 с, обязан прислать «`0400` Реверс: терминал не дождался ответа (F39 = `68`)». Стендин исходную операцию не находит, вычисляет её
`operationId` и отправляет `Reverse`. Процессинг отменяет операцию, если она у него есть,
либо ставит запрет на этот id, если её нет. Третьему механизму остаются операции, по которым
терминал ответ получил, а наша запись об этом потерялась.

**Что это требует от процессинга:** отвечать на `status` и `reverse` по `operationId`,
которого он, возможно, никогда не видел, и хранить запрет на такой id.

## 2. Контракт в стиле REST

Короткие имена `Submit`, `Result`, `GetStatus`, `Reverse` остаются в тексте и на диаграммах
как названия операций. Ниже — как они выглядят на проводе. Транспорт: HTTPS, HTTP/2, mTLS,
JSON.

### 2.1 Мы → процессинг

**`POST /v1/submit`** — передать операцию.

```json
{
  "operationId": "b5.K3F7Q2M9XA4T6R8W1ZB5NC0DEH",
  "operation": "PURCHASE",
  "deadline": "2026-11-16T18:45:27Z",
  "terminalId": "T0012345",
  "merchantId": "M00000000012345",
  "amount": { "value": 150000, "currency": "643" },
  "parentOperationId": null,
  "iso": { "3": "000000", "22": "051", "35": "…", "52": "…", "55": "…" }
}
```

| Код | Тело | Смысл | Что делаем |
|---|---|---|---|
| `202` | `{"status":"ACCEPTED","procRef":"…"}` | Запрос надёжно сохранён и будет обработан | Ждём результат, повторно не шлём |
| `200` | `{"status":"DUPLICATE","state":"IN_PROGRESS"}` | Такой `operationId` уже принят | Берём состояние из ответа |
| `429` + `Retry-After` | `{"status":"BUSY"}` | Не принят, перегрузка | Снижаем лимит, процессинг B или отказ `91 BUSY` |
| `422` | `{"status":"REJECTED","code":"…"}` | Не принят, повтор бессмыслен | Отказ терминалу |
| `5xx`, таймаут, обрыв | — | Неизвестно | `SUBMIT_UNKNOWN`, через 1 с `POST /v1/status` |

**`POST /v1/status`** — узнать судьбу операций. Это чтение, но метод `POST`: в запросе до
100 идентификаторов, в строку адреса они не помещаются.

```json
{ "operationIds": ["b5.K3F7…", "b5.9QW2…"] }
```
```json
{ "items": [
  { "operationId": "b5.K3F7…", "status": "APPROVED",
    "result": { "responseCode": "00", "authCode": "A1B2C3", "rrn": "632021000123" } },
  { "operationId": "b5.9QW2…", "status": "NOT_FOUND" }
] }
```
Статусы: `NOT_FOUND`, `IN_PROGRESS`, `APPROVED`, `DECLINED`, `REVERSED`. Коды: `200`, `429`.

**`POST /v1/reverse`** — отменить операцию.

```json
{
  "operationId": "b5.K3F7Q2M9XA4T6R8W1ZB5NC0DEH",
  "reversalId": "b5.R7M2…",
  "reason": "TIMEOUT",
  "amount": { "value": 150000, "currency": "643" }
}
```
`reason`: `TERMINAL` (пришёл `0400` Реверс), `TIMEOUT` (нет результата за 25 с), `LATE_RESPONSE`
(одобрение не доставлено), `PREAUTH_EXPIRED` (нет второй фазы), `RECONCILIATION` (сверка после
аварии).

| Код | Тело | Смысл |
|---|---|---|
| `202` | `{"status":"ACCEPTED"}` | Реверс принят. Итог (`REVERSED`) придёт вызовом `result` |
| `200` | `{"status":"DUPLICATE","reversalStatus":"REVERSED"}` | По этой операции реверс уже есть, второй не создаётся |
| `404` | `{"status":"NOT_FOUND"}` | Операции нет. Процессинг запомнил запрет: поздний `submit` с этим id получит `422` |
| `429` | `{"status":"BUSY"}` | Повторим позже, реверс лежит у нас в базе |

### 2.2 Процессинг → мы

**`POST /v1/blocks/{block}/result`** — результат. Адрес принимает Callback Router; `{block}` —
префикс `operationId`, по нему Router выбирает блок, не разбирая тело.

```json
{
  "operationId": "b5.K3F7Q2M9XA4T6R8W1ZB5NC0DEH",
  "seq": 1,
  "status": "APPROVED",
  "responseCode": "00",
  "authCode": "A1B2C3",
  "rrn": "632021000123",
  "holdExpiresAt": null,
  "iso": { "55": "…" }
}
```

| Код | Смысл | Что делает процессинг |
|---|---|---|
| `200` | Результат записан в нашу базу | Больше не повторяет |
| `503` + `Retry-After` | Блок переключается или недоступен | Повторяет с растущей паузой |
| `404` | `operationId` нам неизвестен | Не повторяет, у нас срабатывает алерт |

Повтор с теми же `operationId` и `seq` получает `200` и ничего не меняет.

### 2.3 Внутри нашей системы

| Вызов | Кто → кому | Запрос | Ответ |
|---|---|---|---|
| `POST /v1/accept` | ISO-Gateway → блок | Сообщение ISO как есть (`application/octet-stream`), заголовки `X-Connection-Id`, `X-Block-Map-Version` | `202` — блок взял ответственность, ответ придёт через `deliver`; `503` — не принят (в том числе блок здесь больше не работает: БД только читает), шлюз перечитывает карту и повторяет, иначе отвечает терминалу `0210` Ответ на покупку с F39 = `91`, F44 = `HOLD` |
| `POST /v1/deliver` | блок → шлюз из `connectionId` | `{"connectionId":"…","iso":"<base64>"}` | `200 {"result":"DELIVERED"}` или `{"result":"NO_CONNECTION"}` |
| `POST /v1/accept` с `X-Lookup-Done` | ISO-Gateway → текущий владелец, после `404` прежнего | То же, что `accept` | То же; `404` больше не бывает — действует правило «исходная не найдена» |

**Что изменено:** в таблице контракта `preprocessing.md` §1.4 первый столбец теперь содержит
адреса REST.

## 3. HSM — один слой на все блоки? Зачем проверка раз в секунду?

**Да, пул HSM общий для всех шести блоков и обоих стендинов.** HSM — дорогое железо. Свой
набор на каждый блок с резервом дал бы 18 устройств и больше вместо 7. Чтобы общий пул не
связывал блоки, у каждого блока свой лимит одновременных запросов к HSM: зависший HSM или
перегруженный блок не отнимает устройства у остальных.

**Проверку можно делать реже — это параметр.** Период определяет, как быстро мы заметим
отказ: исключаем HSM после 3 неудач подряд, то есть через 3 с при периоде 1 с и через 15 с
при периоде 5 с. Выбран 1 с, потому что проверка почти ничего не стоит: одна операция в
секунду с каждого пода при мощности HSM 10 000 операций в секунду — доли процента.

Есть и вторая защита, она не зависит от периода: HSM исключается и по ошибкам боевых
запросов (3 таймаута подряд). При полной нагрузке она срабатывает раньше проверки.

Зачем тогда проверка, если есть боевые запросы:
- **Резервные HSM.** Два из семи стоят в запасе и боевых запросов не получают. Без проверки
  об их поломке мы узнали бы в момент, когда они понадобились.
- **Неверные ключи.** Проверка считает MAC на тестовом ключе и сравнивает с известным
  значением. HSM, который после обслуживания отвечает быстро, но с неправильными ключами,
  иначе отклонял бы MAC исправных терминалов.
- **Возврат в работу.** Исключённый HSM боевых запросов не получает, и только проверка
  показывает, что он снова исправен.

## 4. etcd: как шлюзы получают кольцо и карту, кто поддерживает данные, как работает Raft

### 4.1 Что это за компонент

«Routing Config» — это не приложение, а **данные в отдельном кластере etcd из 5 узлов**.
В нём лежит всё, от чего зависит, куда пойдёт сообщение терминала.

| Ключ | Что лежит | Кто меняет | Как часто |
|---|---|---|---|
| `/routing/ring` | Кольцо: ~1 500 точек (6 блоков × 256 виртуальных узлов), несколько десятков килобайт | Инженер, при добавлении блока | Раз в месяцы |
| `/routing/ring-history/<версия>` | Прежние кольца: нужны, чтобы найти прежнего владельца терминала | Вместе с кольцом | Раз в месяцы |
| `/routing/blockmap/b1…b6` | Где сейчас работает логический блок: `B5`, `SI1` или `HOLD` | Failover Orchestrator | При релизах и авариях |
| `/routing/processing` | Правила выбора процессинга A или B | Инженер | Редко |
| `/routing/override/…` | Группы терминалов, переведённые с монолита (миграция) | Инженер | На время миграции |
| `/orchestrator/leader` | Отметка «я активный экземпляр оркестратора» с ограниченным сроком | Failover Orchestrator | Продлевается каждые несколько секунд |

**Номер версии** настроек — это `revision` самого etcd: счётчик, который растёт на единицу
при каждой записи в кластер. Он общий для всех, его не надо вести самим. Именно его шлюз
передаёт блоку в заголовке `X-Block-Map-Version`.

### 4.2 Как шлюз получает настройки — подпиской, а не опросом

1. **Запуск.** Шлюз читает копию настроек со своего диска: так он стартует, даже если etcd
   недоступен. Затем подключается к etcd (адреса всех 5 узлов, mTLS, учётная запись только
   на чтение) и читает всё под `/routing/` одним запросом. В ответе приходит `revision` R.
2. **Подписка (watch).** Шлюз открывает долгоживущий поток gRPC: «присылай всё, что
   изменится под `/routing/`, начиная с R + 1». Запись в etcd доходит до шлюза за
   миллисекунды. Шлюз ни о чём не спрашивает — etcd сам присылает изменение.
3. **Применение.** Шлюз проверяет изменение (формат, версия больше текущей), строит новую
   таблицу в памяти и подменяет указатель на неё. Запросы, которые уже обрабатываются,
   дорабатывают со старой таблицей. Новая копия пишется на диск.
4. **Обрыв потока.** Клиент подключается к другому узлу и продолжает с последней полученной
   версии: etcd хранит историю изменений, поэтому ничего не теряется. Если история уже
   вычищена, шлюз перечитывает всё целиком.
5. **Страховка.** Раз в 30 с шлюз сверяет свою версию с etcd — на случай зависшей подписки.
   Версия каждого шлюза видна в метриках; расхождение дольше 10 с — алерт.

Так же настройки получает Callback Router. Приложения блоков в etcd не ходят — см.
[`my-questions-answers-2.md`](my-questions-answers-2.md), ответ 10.

**Поиск блока** в памяти шлюза: хеш от F41 и двоичный поиск по ~1 500 точкам, около 100 нс.
В etcd на каждое сообщение никто не ходит.

### 4.3 Кто поддерживает данные в актуальном состоянии

Писать в etcd могут только двое, у остальных учётные записи на чтение.

- **Failover Orchestrator** меняет карту блоков: при аварии сам, при релизе по команде.
- **Инженер через конвейер.** Изменение кольца, правил и переводов терминалов — это правка
  файла в репозитории, проверка вторым человеком, затем конвейер проверяет файл и записывает
  его в etcd утилитой. Руками в etcd никто не пишет.

Каждая запись — это транзакция etcd с условием «записать, только если ключ с версии N не
менялся». Два писателя не затрут изменения друг друга: второй получит отказ и перечитает.

Согласованность самих пяти узлов поддерживает Raft (ниже). Эксплуатации остаётся:

| Задача | Как |
|---|---|
| Резервная копия | Снимок раз в час, хранится вне кластера |
| Место на диске | Автоочистка старых версий, периодическая дефрагментация по одному узлу |
| Замена узла | Вывести из состава, добавить новый — он сам догонит остальных |
| Наблюдение | Есть ли лидер, частота его смен, время записи на диск, размер базы |
| Железо | Отдельные VM с быстрым SSD: скорость etcd определяется скоростью записи на диск |

### 4.4 Что будет, если etcd недоступен

Транзакции идут как шли: шлюзы и блоки работают по копии в памяти. Нельзя только менять
настройки — в том числе переводить блок в стендин. Поэтому etcd из 5 узлов в разных стойках:
он переживает отказ любых двух.

### 4.5 Как работает Raft

**Задача.** Пять узлов должны хранить одинаковые данные и не разойтись при отказах узлов и
сети. Raft решает её так: все изменения идут через одного лидера и считаются принятыми
только после записи на большинстве узлов.

**Роли.** В каждый момент узел — лидер, ведомый или кандидат. Лидер один.

**Срок (term).** Время поделено на пронумерованные сроки. В каждом сроке не больше одного
лидера. Номер срока есть в каждом сообщении; узел, увидевший номер больше своего, сразу
признаёт, что отстал, и становится ведомым.

**Выборы лидера**
1. Лидер каждые 100 мс шлёт ведомым сигнал «я жив».
2. Ведомый, не получавший сигнал около 1 с, становится кандидатом: увеличивает номер срока,
   голосует за себя и просит голоса у остальных. Срок ожидания у каждого узла немного
   разный и случайный, чтобы кандидаты не появлялись одновременно.
3. Узел отдаёт голос один раз за срок и только кандидату, чей журнал не короче его
   собственного. Поэтому лидером не станет узел, у которого нет принятых записей.
4. Кандидат, получивший 3 голоса из 5, становится лидером. Смена лидера занимает 1–2 с;
   на это время запись в etcd останавливается, чтение копий в шлюзах — нет.

**Запись**
1. Клиент отправляет запись лидеру (ведомый перенаправит её сам).
2. Лидер дописывает запись в свой журнал на диск и рассылает ведомым.
3. Ведомый пишет запись на диск и подтверждает.
4. Когда запись лежит на диске у 3 узлов из 5, включая лидера, она **принята** (committed):
   лидер применяет её к базе, увеличивает `revision` и отвечает клиенту. Только после этого
   изменение уходит подписчикам.
5. Отставшие ведомые получают запись позже. Сильно отставшему лидер шлёт снимок базы.

Запись стоит одну запись на диск и один обмен по сети — единицы миллисекунд.

**Почему двух лидеров с разными данными быть не может**

| Ситуация | Что происходит |
|---|---|
| Упал лидер | Через ~1 с ведомый выигрывает выборы. Принятые записи есть у большинства, а значит, и у нового лидера |
| Упали 2 узла из 5 | Осталось 3 — большинство. Кластер работает |
| Упали 3 узла из 5 | Большинства нет: записи не принимаются. Данные не расходятся, кластер ждёт |
| Сеть разделила узлы на 2 и 3 | Сторона из 3 выбирает лидера и работает. Прежний лидер на стороне из 2 не может набрать 3 подтверждения, ничего не принимает и слагает полномочия |
| Старый лидер вернулся | Видит срок больше своего, становится ведомым. Его непринятые записи заменяются журналом нового лидера |

**Чтение.** По умолчанию etcd читает согласованно: лидер перед ответом убеждается у
большинства, что он всё ещё лидер. Узел, отрезанный от большинства, на такое чтение не
ответит и устаревшие данные не отдаст.

**Почему 5 узлов.** Большинство от 5 — это 3, значит, переживаем 2 отказа: один узел на
обслуживании и один сломался. 3 узла переживают один отказ. 4 и 6 не дают ничего сверх 3 и 5:
большинство от 4 — тоже 3.

**Что спросят на защите**

| Вопрос | Ответ |
|---|---|
| Стоит ли Raft на пути транзакции? | Нет. Транзакция читает копию в памяти шлюза |
| Зависит ли Raft от точности часов? | Корректность — нет, только номера сроков и большинство. От часов зависит срок отметки лидера оркестратора, поэтому на неё одну мы не полагаемся: каждая запись оркестратора идёт с условием «я всё ещё владею отметкой», а блок отклоняет запросы по старой версии карты |
| Что, если шлюз не получил новую версию? | Он шлёт запросы по старой карте. Прежнее место блока только читает и отвечает `503`, шлюз перечитывает настройки |
| Почему не PostgreSQL? | Нужны подписка на изменения, общий номер версии и работа при отказе двух узлов без ручного переключения. В etcd это есть из коробки |
| Почему этот etcd отдельный от etcd в блоках? | У каждого блока свой etcd из 3 узлов для выбора primary базы. Общий etcd стал бы общей точкой отказа для всех блоков |

**Что изменено:** на общей схеме etcd — отдельный компонент, добавлена схема
[`diagrams/routing-config-etcd.mmd`](diagrams/routing-config-etcd.mmd), раздел «Управление» в
[`layers.md`](layers.md) дополнен.

## 5. «Нет ответа 10 с — терминал переподключается»: ответа на что? Почему не повтор?

**Это про эхо, а не про операцию.** У терминала два разных срока.

| Что ждём | Срок | Что делает терминал, если ответа нет |
|---|---|---|
| Ответ на эхо `0800` | 10 с | Закрывает соединение и открывает новое |
| Ответ на операцию (`0200` Покупка, `0100` Предавторизация, `0220` Завершение) | 30 с | Показывает отказ, сохраняет и отправляет реверс `0400` |

**Почему на молчание в ответ на эхо — переподключение.** Эхо отправляется только в простое
и проверяет одно: живо ли соединение. Шлюз отвечает на него сам за миллисекунды. Если за
10 с ответа нет, соединение мертво (его закрыло сетевое оборудование по пути или пропал
шлюз), и повторять эхо в то же соединение бессмысленно: TCP и так сам повторял отправку
все эти 10 с.

**Почему операцию не повторяем в том же соединении.** TCP гарантирует доставку, пока
соединение живо: раз оно живо, запрос у нас уже есть, и повтор только создаст дубликат.
Повтор (`0201`) нужен в одном случае — соединение оборвалось до ответа. Тогда терминал
переподключается и шлёт повтор, чтобы забрать ответ, который ждёт его в базе блока.

«Шлюз закрывает соединение, молчащее 150 с» — проверка с другой стороны: исправный терминал
шлёт эхо раз в 60 с; если два эхо подряд не пришли, соединение мертво и шлюз освобождает
сокет.

## 6. Куда доходит эхо-запрос и кто на него отвечает?

Эхо доходит до **ISO-Gateway и дальше не идёт**. Шлюз сам формирует `0810` Ответ на сетевой запрос: копирует F7,
F11 и F70 из запроса, ставит F39 = `00` и кладёт время сервера в F48. MAC в эхо нет:
у шлюза нет доступа к HSM.

В блок, базу, HSM и процессинг эхо не попадает. Это сделано намеренно: в худшем случае эхо —
это 1 700 сообщений в секунду, и они не должны нагружать путь транзакций.

Следствие: успешное эхо означает, что живы сеть, маршрутизатор и процесс шлюза. О здоровье
блока и процессинга оно не говорит — терминалу это и не нужно, при их отказе он получит `91 HOLD` или `91 BUSY`
на саму операцию.

## 7. Как работает mTLS на всём пути? Рукопожатие — один раз?

**Сквозного TLS от терминала до процессинга нет.** Каждый участок — отдельное соединение
со своим рукопожатием и своими ключами. Шлюз обязан расшифровать сообщение, чтобы прочитать
F41 и выбрать блок.

| Участок | Кто предъявляет сертификат | Что проверяется |
|---|---|---|
| Терминал → ISO-Gateway | Шлюз — всегда. Терминал — если включаем клиентские сертификаты (рекомендую: прошивка наша) | Терминал: сертификат шлюза подписан нашим центром, зашитым в прошивку. Шлюз: сертификат терминала действителен и не отозван, номер терминала в нём совпадает с F41 |
| ISO-Gateway → блок (`accept`) | Оба | Блок принимает `accept` только от сертификатов шлюзов |
| Блок → ISO-Gateway (`deliver`) | Оба | Шлюз принимает `deliver` только от блоков |
| Блок → HSM | Оба | Отдельный сегмент сети; способ зависит от модели HSM |
| Блок → процессинг | Оба | Сертификаты сторон, согласованные с процессингом |
| Процессинг → Callback Router → блок | Оба на каждом участке | Плюс список разрешённых адресов процессинга |
| Приложения → PostgreSQL, клиенты → etcd | Оба | Учётная запись привязана к сертификату |

Внутренние сертификаты выдаёт наш центр сертификации через Vault, срок жизни короткий,
перевыпуск автоматический.

**Да, рукопожатие выполняется один раз при открытии соединения.** После него данные
шифруются быстрым симметричным шифром на ключах, выведенных при рукопожатии.
- Соединение терминала живёт часами — одно рукопожатие на всё это время.
- Внутри ЦОД сервисы держат пулы постоянных соединений HTTP/2. Рукопожатие — при создании
  соединения, а не на каждый запрос.
- При переподключении терминал возобновляет прежнюю сессию TLS: сокращённое рукопожатие без
  повторной проверки сертификатов, в несколько раз дешевле для процессора шлюза. Это важно,
  когда переподключаются сразу 12 500 терминалов упавшего шлюза.

**Этапы рукопожатия (TLS 1.3 со взаимной проверкой)**

| # | Кто | Что отправляет | Зачем |
|---|---|---|---|
| 1 | Клиент | ClientHello: версии, шифры, случайное число, открытая половина одноразового ключа | Предложить параметры и начать обмен ключами |
| 2 | Сервер | ServerHello: выбранный шифр, своё случайное число, своя половина ключа | С этого момента у сторон общий секрет; всё дальше зашифровано |
| 3 | Сервер | Запрос сертификата клиента | Это и делает TLS взаимным |
| 4 | Сервер | Свой сертификат и подпись всего предыдущего обмена закрытым ключом | Доказать, что он владелец сертификата, а не тот, кто его скопировал |
| 5 | Сервер | Finished: контрольная сумма всего обмена | Доказать, что обмен никто не изменил |
| 6 | Клиент | Проверяет цепочку сертификата, имя, срок, отзыв. Отправляет свой сертификат, свою подпись и Finished | То же в обратную сторону |
| 7 | Обе | Выводят ключи шифрования данных из общего секрета | Дальше идут данные |

На всё уходит один обмен «туда-обратно» до начала передачи данных (в TLS 1.2 — два).
Ключи каждого соединения одноразовые: если закрытый ключ сертификата украдут, записанный
ранее трафик расшифровать не получится.

## 8. Корректно ли название `sessionId`?

**Вы правы, название было неточное — переименовано в `connectionId`.** По смыслу это
идентификатор **TCP-соединения терминала на конкретном шлюзе**, то есть обратный адрес для
ответа. Он создаётся при приёме соединения, умирает вместе с сокетом и ничего о логической
сессии терминала не хранит.

Слово «сессия» вводило в заблуждение по трём причинам:
- в карточном мире сессия — это период от sign-on до sign-off и сессионные ключи; ключи у
  нас меняются раз в сутки и переживают десятки соединений;
- двухфазная операция — тоже «сессия» в бытовом смысле, а она к соединению как раз не
  привязана;
- читатель ждёт, что по идентификатору можно найти состояние, а его там нет.

**Что изменено:** во всех документах и схемах `sessionId` → `connectionId`, столбец
`session_id` → `connection_id`, ответ шлюза `NO_SESSION` → `NO_CONNECTION`, заголовок
`X-Session-Id` → `X-Connection-Id`. Состав не менялся: версия, номер шлюза, время запуска
шлюза, случайная часть.

## 9. Как гарантируем, что история в аудите полная, если старые партиции удаляются?

Гарантия состоит из двух частей: событие не теряется по дороге, и партиция не удаляется,
пока это не проверено.

**Почему событие не теряется по дороге**

| Участок | Что защищает |
|---|---|
| Приложение → база | Событие пишется в `txn_events` в той же транзакции, что и смена состояния. Смены без события не бывает |
| База → Kafka | События читаются из журнала базы через слот репликации. База не удаляет журнал, пока читатель не подтвердил получение. Слот переживает смену primary |
| Kafka | Три копии, запись подтверждается двумя |
| Kafka → ClickHouse и WORM | Позиция в Kafka сдвигается только после записи в хранилище. Повторно доставленное событие отбрасывается по ключу `txn_id + seq` |

Такая цепочка может доставить событие дважды, но не может потерять молча: сбой на любом
участке останавливает поток, а не пропускает событие.

**Проверка перед удалением партиции.** Партицию удаляет не расписание само по себе, а
задание с условиями. Все четыре должны выполниться:

1. Читатель журнала подтвердил позицию позже последнего изменения в этой партиции.
2. Число событий и контрольная сумма за этот день в базе и в ClickHouse совпадают.
3. У каждой транзакции дня номера событий идут без пропусков и есть конечное состояние,
   либо она перенесена в таблицу открытых предавторизаций.
4. Суточный бэкап, содержащий эту партицию, завершён и проверен.

Не выполнилось — партиция остаётся, срабатывает алерт. Диск рассчитан на запас в несколько
дней сверх трёх «горячих».

**Вторая независимая копия.** Бэкап базы (ежедневный полный и непрерывный архив журнала)
не проходит через Kafka и ClickHouse. Если в аудите всё же найдётся дыра, день
восстанавливается из бэкапа.

**Если читатель журнала надолго остановился.** Журнал копится на диске базы. Чтобы он не
занял весь диск, стоит предел; при превышении слот сбрасывается, и поток восстанавливается
перечитыванием самих таблиц. Три дня хранения в блоке — это и есть время на такую починку.

**Защита от правки задним числом.** Каждое событие несёт хеш предыдущего события той же
транзакции, копия лежит в хранилище с запретом изменения.

## 10. «Доставить в срок не удалось» — какой срок? Почему 25 с? Что, если у терминала 10 с?

**Срок — это время ожидания терминала, 30 с от первой отправки.** Сервер ведёт свой срок
T2 = 25 с от первого приёма запроса.

**На 25-й секунде возможны два разных события, они не накладываются:**

| Что известно к 25-й секунде | Что делаем |
|---|---|
| Процессинг результат так и не дал | Отказ терминалу `91 LATE`, автореверс с причиной `TIMEOUT` |
| Результат «одобрено» получен раньше, но соединения с терминалом нет и повтора не было | Автореверс с причиной `LATE_RESPONSE` |

**Почему 25.** Это не стандарт, а расчёт: срок терминала минус запас 5 с. Запас нужен,
чтобы отказ `91 LATE` успел дойти до терминала раньше, чем тот сам покажет отказ. В него входят:
разница между отправкой с терминала и приёмом у нас, шаг Timeout Monitor (1 с), подпись и
доставка ответа, задержки сети.

**Оба числа берутся из одного источника.** Срок терминала — параметр сервера настроек (TMS).
Блок знает профиль настроек терминала из справочника и считает T2 как «срок этого терминала
минус 5 с». Сейчас в документах стоит одно число на всех; для терминалов с разными сроками
T2 должен считаться по профилю — это уточнение я предлагаю принять.

**Если терминал делает реверс уже через 10 с, а сервер считает, что у него 30.** Деньги не
пострадают, потому что главный механизм — реверс терминала, а наш автореверс — страховка на
случай, когда терминал прислать реверс не может.

| Момент | Что происходит |
|---|---|
| 10 с | Терминал показывает отказ и шлёт `0400` Реверс |
| 10 с + мс | Блок видит операцию в ожидании результата и сразу отправляет `Reverse`, не дожидаясь своих 25 с |
| Позже пришло «одобрено» | Процессинг обязан применить реверс и к уже одобренной операции. Терминал ответ на операцию, которую уже не ждёт, отбрасывает |
| 25 с | Timeout Monitor видит, что операция уже в реверсе, и ничего не делает |

Плохо в таком расхождении только одно: лишние отказы для клиентов. Обратная ситуация
(у терминала срок больше нашего) безопасна — он получит `91 LATE` на 25-й секунде.

**Что изменено:** в `iso8583.md` §7.2 добавлено правило прошивки №13 — ответ на операцию,
которую терминал уже не ждёт, отбрасывается.

## 11. Кто определяет срок жизни предавторизации?

**Не мы.** Срок задают правила платёжной системы и банк: он зависит от типа операции и
категории торговой точки (гостиницы и прокат держат блокировку дольше, чем магазин). Сама
блокировка денег находится у эмитента, и снимает он её по своим правилам.

Для нас источник правды — процессинг. Способы получить срок, от лучшего к худшему:
1. Процессинг возвращает срок в результате предавторизации — поле `holdExpiresAt` в
   `result` (см. ответ 2). Мы записываем его в `deadline_at`.
2. Срок берётся из справочника торговых точек по категории точки.
3. Одно значение по умолчанию.

Наш срок нужен, чтобы закрыть свою запись и, если вторая фаза не пришла, отправить реверс —
тогда блокировка снимается сразу, а не по правилам эмитента.

Это открытый вопрос заказчику: «+7 дней» в сценарии 6 — пример.

## 12. Timeout Monitor: блокировка, период, размер пачки, откуда `deadline_at`

**Да, `SELECT … FOR UPDATE SKIP LOCKED`.** Строку, занятую одним экземпляром, второй
пропускает, а не ждёт.

Блокировка держится миллисекунды, а не всё время вызова процессинга. Работа идёт в три шага:

```sql
-- Шаг 1. Забрать пачку и отодвинуть срок: строка «занята» на 5 с
WITH due AS (
  SELECT txn_id, msg_ts FROM transactions
  WHERE status IN ('RECEIVED','SUBMIT_UNKNOWN','ACCEPTED','AUTHORIZED','REVERSAL_PENDING')
    AND deadline_at <= now()
  ORDER BY deadline_at
  LIMIT 500
  FOR UPDATE SKIP LOCKED
)
UPDATE transactions t
SET deadline_at = now() + interval '5 seconds'
FROM due WHERE t.txn_id = due.txn_id AND t.msg_ts = due.msg_ts
RETURNING t.*;
-- Шаг 2. Вне транзакции: вызов процессинга (status или reverse)
-- Шаг 3. Записать итог с проверкой версии строки (UPDATE … WHERE version = :v)
```

Если экземпляр упал после шага 1, через 5 с строку заберёт другой.

**Почему раз в секунду.** Период — это точность, с которой соблюдаются сроки.
- Самый короткий срок — 1 с: проверка статуса после `Submit` без ответа.
- Запас между нашим сроком (25 с) и сроком терминала (30 с) — 5 с. Опрос раз в 5 с съел бы
  его целиком.

Реже делать нельзя без потери точности, а чаще — незачем. Запрос дешёвый: он идёт по
индексу, в котором только незавершённые операции с истёкшим сроком. В штатном режиме таких
строк единицы.

**Размер пачки — предлагаю 500 строк.** Если пачка вернулась полной, следующая забирается
сразу, без паузы. Настоящий ограничитель — не размер пачки, а бюджет вызовов процессинга:
`status` и `reverse` вместе занимают не больше 5 % лимита, чтобы после его восстановления не
обрушить на процессинг все накопленные проверки разом.

**Кто заполняет `deadline_at`.** Тот сервис, который переводит операцию в новое состояние,
в том же запросе к базе. Значение — «когда на эту строку надо посмотреть в следующий раз».

| Состояние | Кто пишет | Значение | Что сделает Timeout Monitor |
|---|---|---|---|
| `RECEIVED` | Transaction Receiver | приём + 2 с | Под упал до отправки: `status`, затем запрет и отказ `91 LATE` |
| `SUBMIT_UNKNOWN` | Processing Sender | + 1 с | `status` |
| `ACCEPTED` | Processing Sender | приём + 5 с (T1) | `status`; ставит следующий срок — приём + 25 с (T2) |
| `ACCEPTED` на T2 | Timeout Monitor | — | Отказ `91 LATE`, автореверс |
| `APPROVED`, ответ не доставлен | Result Receiver | приём + 25 с | Автореверс `LATE_RESPONSE` |
| `AUTHORIZED` | Result Receiver | срок предавторизации (ответ 11) | Реверс |
| `REVERSAL_PENDING` | Тот, кто начал реверс | сейчас, затем с растущей паузой | `reverse`, пока процессинг не примет |

Сами числа (2 с, 5 с, 25 с) — настройки блока; 25 с считается от срока терминала (ответ 10).

## 13. Почему повторный `0400` и наш автореверс не создают второй реверс?

Защиты две, и первая — наша: **мы не отправляем второй реверс.**

1. **У нас.** Перед реверсом блок находит исходную операцию и смотрит её состояние. Если она
   уже в реверсе, новый `Reverse` не создаётся, терминал получает сохранённый `0410` Ответ на реверс.
   Одновременный приход `0400` Реверс и срабатывание Timeout Monitor разводит версия строки:
   перевести операцию в `REVERSAL_PENDING` удаётся одному, второй перечитывает строку и
   видит, что реверс уже идёт.
2. **У процессинга.** На один `operationId` действует один реверс. Второй запрос получает
   `DUPLICATE` со статусом первого. Эта защита нужна на случай, когда наша отметка
   потерялась: например, блок переехал в стендин, и запись о начатом реверсе не успела туда
   дойти.

## 14. Зачем пять отдельных приложений в блоке? Можно ли объединить?

**Можно — объединено.** Пять отдельных конвейеров сборки при одной команде — лишняя цена.
Теперь это **один репозиторий, один образ, три роли запуска.**

| Роль | Что входит | Почему отдельно от остальных |
|---|---|---|
| **Request** (путь запроса) | Transaction Receiver + Processing Sender | Это один синхронный путь: приём, проверки, запись, `submit`. Между ними нет очереди; разнесение по двум приложениям добавляет сетевой вызов и точку отказа ровно между записью `RECEIVED` и отправкой |
| **Response** (путь ответа) | Result Receiver + Delivery | Тоже один путь: результат, запись, подпись, `deliver` |
| **Timeout Monitor** | Сроки, проверки статуса, автореверсы | Фоновая работа, а не обработка запросов. При сбое процессинга она резко растёт и не должна отнимать процессор и соединения с базой у онлайн-пути. Экземпляров нужно 2, а не 30 |

Что это даёт: один конвейер и одна версия на блок вместо пяти, нет несовместимости версий
между частями одного пути, меньше сетевых вызовов.

**Что остаётся раздельным и почему**

| Причина | Пояснение |
|---|---|
| Разный запуск | Входящий путь запускают шлюзы, обратный — процессинг, Timeout Monitor — время |
| Разное поведение при сбое | Процессинг недоступен: входящий путь быстро отказывает, обратный простаивает, Timeout Monitor работает больше всех |
| Разный масштаб | Онлайн-пути масштабируются по TPS, Timeout Monitor — нет |
| Разные сетевые права | Входящий путь принимает вызовы только от шлюзов, обратный — только от Callback Router. Правила сети задаются на роль |

Внутри образа пять частей остаются отдельными модулями с понятными границами. Поэтому
названия на схемах верны как названия функций; меняется только упаковка.

**Довод против объединения входящего пути.** Лимит одновременных запросов к процессингу
точнее, когда его держат 3–4 экземпляра Processing Sender, а не 30 экземпляров общего
приложения, каждый со своей долей. Я считаю этот довод слабее выигрыша от упрощения:
лимит адаптивный, и каждый экземпляр подстраивает свою долю сам.

**Что изменено:** роли описаны в `layers.md` (слой 4) и `preprocessing.md`, показаны рамками
на общей схеме и на схеме блока, в расчёт мощности добавлены роли Response и Timeout Monitor.

## 16. `TCP_USER_TIMEOUT` 10 с при эхо раз в 60 с — как это сочетается?

Это три разных механизма для трёх разных случаев.

| Механизм | Кто | Когда работает | Что ловит |
|---|---|---|---|
| Эхо раз в 60 с простоя, ответ ждём 10 с | Терминал | Терминал простаивает | Терминал узнаёт, что соединение мертво |
| Закрытие соединения, молчащего 150 с | Шлюз | Терминал простаивает | Шлюз узнаёт, что терминал пропал, и освобождает сокет |
| `TCP_USER_TIMEOUT` 10 с | Ядро ОС шлюза | Шлюз **отправил данные**, а подтверждения TCP нет | Шлюз узнаёт, что ответ не доходит |

Эхо не помогает в самый важный момент: мы записали в сокет ответ `0210`, а терминал уже
недоступен. Без настройки Linux повторяет отправку около 15 минут, и всё это время шлюз
считает соединение живым.

**Что происходит по истечении 10 с:**
1. Ядро закрывает соединение и сообщает шлюзу об ошибке.
2. Шлюз удаляет запись о соединении из своей таблицы.
3. Следующий `deliver` в это соединение получает `NO_CONNECTION`.
4. Ответ остаётся в базе блока. Терминал переподключится и заберёт его повтором; если
   повтора не будет, на 25-й секунде сработает автореверс.

Ограничение: тот `deliver`, чьи байты зависли, уже получил ответ `DELIVERED`. Поэтому
`DELIVERED` мы не считаем доказательством получения, а последняя страховка — реверс самого
терминала через 30 с.

## 17. Почему перехваченный пакет нельзя переслать? Разве нельзя отправить те же байты?

Отправить можно — получатель их не примет. Перехватчик видит не сообщение ISO, а
зашифрованную запись TLS.

| Что делает перехватчик | Почему не работает |
|---|---|
| Шлёт запись повторно **в то же соединение** | У каждой записи порядковый номер, он участвует в проверке целостности. Получатель ждёт номер N + 1, а запись сделана под номер N. Проверка не сходится, соединение рвётся |
| Открывает **своё соединение** и шлёт запись туда | У каждого соединения свои ключи: они выводятся из одноразовых значений, которые обе стороны создают при рукопожатии. Чужую запись новым ключом не расшифровать |
| Воспроизводит **всё соединение** с рукопожатием | Сервер каждый раз присылает новое случайное значение. Записанные ответы клиента к нему не подходят, рукопожатие не завершается |

Исключение одно: «ранние данные» TLS 1.3 (0-RTT) воспроизвести можно. На шлюзах этот режим
выключен.

**От чего TLS не защищает:** от того, у кого есть сообщение в открытом виде — взломанный
терминал или программа на нём. Для этого остальные рубежи: MAC, окно времени по F7 и ключ
идемпотентности. Повтор того же сообщения новой операцией не станет.

**Что изменено:** формулировка в `task-answers.md` и `preprocessing.md` §8 уточнена — «ни в
том же, ни в другом соединении».

## 18. Где отсекаются сообщения вне окна времени? Блокировка по IP? Где и какой rate limiting?

**Окно времени проверяется в блоке**, в Transaction Receiver, пятым шагом — после проверки
MAC. Порядок выбран намеренно: сначала убеждаемся, что сообщение от настоящего терминала и
F7 не подменён, и отказ `30 TIME` уходит подписанным.

**Блокировать по IP — плохая идея для нашего случая.** Терминалы магазина или сотового
оператора выходят в сеть через один общий адрес. Заблокировав его, отключим сотни исправных
терминалов. Блокировать надо **терминал**: шлюз знает его номер и сертификат.

**Rate limiting ставится на трёх уровнях, и каждый видит своё.**

| Уровень | Что видит | Что ограничивает | Чего не может |
|---|---|---|---|
| Защита провайдера, пограничный экран, маршрутизаторы | IP-адреса и порты | Объёмные атаки, поток SYN, число новых соединений в секунду с одного адреса. Если терминалы приходят из известных сетей — список разрешённых сетей | Не видит внутрь TLS: ни номера терминала, ни числа сообщений |
| **ISO-Gateway — основное место** | Соединение, сертификат, F41, каждое сообщение | См. таблицу ниже | — |
| Блок | Операции | Число одновременных запросов на блок, к HSM, к процессингу | — |

**Ограничения на шлюзе (числа — предлагаю как начальные)**

| Что | Предел | При превышении |
|---|---|---|
| Сообщений с одного соединения | 5 в секунду, всплеск до 10 | Отказ `91 RATE`, при повторении — закрытие соединения |
| Финансовых операций в полёте на терминал | 1 | Отказ `91 RATE` |
| Соединений на один терминал | 1; новое вытесняет старое | Старое закрывается |
| Новых соединений с одного IP | 50 в секунду (с учётом общих адресов) | Соединение не принимается |
| Рукопожатий TLS на шлюз | 20 000 в секунду | Лишние ждут в очереди, затем отказ |
| Запросов в полёте на шлюз | По мощности шлюза | Отказ `91 RATE` |
| Отказов подряд по формату, MAC или времени с одного терминала | 20 в минуту | Соединение закрывается, терминал помечается в справочнике, алерт |

Алгоритм — «ведро с жетонами» (token bucket) в памяти шлюза. Общего хранилища счётчиков не
нужно: соединение терминала целиком живёт на одном шлюзе.

**Если сообщений вне окна очень много.** От исправного терминала такого потока быть не может:
часы подводятся по каждому ответу `0810`. Значит, это сбой прошивки или взлом, и срабатывает
последняя строка таблицы: терминал блокируется по номеру, его сертификат отзывается.

## 19. L3-маршрутизаторы или L4-балансировщики на границе? Или L3 → L4 → шлюзы?

**Заменить L3 на L4 нельзя, можно только добавить L4 между ними.** Маршрутизаторы — это сама
сеть: пакет до любого нашего устройства кто-то должен довести. Балансировщики L4 тоже
получают трафик от маршрутизаторов через ECMP. Поэтому выбор такой: «L3 → шлюзы» или
«L3 → L4 → шлюзы».

**Что дал бы слой L4**

| Возможность | Сейчас, без L4 | С L4 |
|---|---|---|
| Вывод шлюза на релиз | Жёсткий разрыв: 12 500 терминалов переподключаются | Плавный: новые соединения не даём, старые доживают |
| Возврат шлюза | Часть соединений на **других** шлюзах рвётся | Ничего не рвётся: балансировщик помнит соединения |
| Смена пути у провайдера | Соединение может попасть на чужой шлюз | Не важно, на какой L4 попал пакет: хеш у всех одинаковый |
| Защита от потока SYN | На экране и шлюзе | Дополнительно на L4 |

**Чего это стоит:** ещё 2–4 узла, их настройки, релизы и отказы; команда, которая это умеет.
Единой точкой отказа слой не станет — узлы L4 стоят за тем же ECMP и взаимозаменяемы, — но
сбоев и состояний станет больше.

**Почему сейчас без L4.** Переподключение терминала у нас штатный сценарий: терминал
возвращается за 0–5 с, незавершённую операцию забирает повтором, деньги защищены реверсом.
Главное достоинство L4 — не рвать соединения — нам полезно, но не обязательно.

**Моя рекомендация: начинать без L4 и добавить его по измеримым признакам.**

| Признак | Почему это повод |
|---|---|
| Маршрутизаторы банка не умеют resilient hashing | Тогда любой отказ шлюза рвёт соединения на всех шлюзах |
| Релизы шлюзов чаще раза в месяц | Каждый релиз — 8 жёстких разрывов по 12 500 терминалов |
| Разрывы из-за смены пути или возврата шлюза заметны в метриках | Теория из §1.8 подтвердилась на практике |
| Операции, прерванные переподключением, съедают заметную долю бюджета 99,99 % | Плавный вывод окупается |

Если в банке уже есть аппаратные балансировщики и команда при них — довод за L4 сильнее,
цена ниже. Самый сильный довод за L4 — плавный вывод шлюза при релизе; если заказчик скажет,
что шлюзы обновляются часто, слой стоит ввести сразу.

## 20. «Терминал переключается, только когда у него нет открытых операций» — как?

**Отдельного сервиса нет, решение принимает шлюз.** Он и так считает запросы в полёте по
каждому терминалу — это нужно для ограничения нагрузки.

Как идёт переключение:
1. Инженер добавляет группу терминалов в список перевода в etcd.
2. Шлюз получает изменение по подписке, но применяет его к терминалу **между сообщениями**:
   когда у терминала нет запроса, на который ещё не пришёл ответ.
3. Если запрос в полёте, шлюз ждёт ответа монолита или истечения 30 с и только потом
   начинает слать сообщения этого терминала в новый блок.

**Уточнение формулировки.** «Открытая операция» здесь — запрос, ждущий ответа. Дождаться,
пока у терминала не останется предавторизаций без второй фазы и покупок, которые ещё можно
отменить, нельзя: они живут днями. Для них работает пересылка прежнему владельцу (ответ 21).

## 21. По какому признаку сообщения по старым операциям уходят монолиту?

> Пересмотрено во втором раунде (ответ 10 в [`my-questions-answers-2.md`](my-questions-answers-2.md)):
> приложения блоков в etcd не ходят, поэтому историю владельцев читает шлюз.

**Маршрутизирует шлюз — по времени исходной операции.** У шлюза есть история кольца и
переводов терминалов (`/routing/ring-history`, `/routing/override`). Терминал переводится
только между сообщениями, поэтому всё, что сделано до момента перевода, лежит у прежнего
владельца.

| Шаг | Что делает шлюз | Поля ISO |
|---|---|---|
| 1 | Определяет, что сообщение ссылается на уже существующую операцию | MTI: `0400` Реверс/`0401` Повтор реверса (реверс), `0220` Завершение/`0221` Повтор завершения (вторая фаза), `0201` Повтор покупки/`0101` Повтор предавторизации (повтор) |
| 2 | Берёт время исходной операции | Для реверса и второй фазы — время из F90 (исходные MTI, STAN, дата и время). Для повтора — F7 самого сообщения |
| 3 | Сравнивает с моментом перевода терминала по F41 | F41 + история кольца и переводов |
| 4 | Исходная раньше перевода и срок пересылки не истёк — `accept` прежнему владельцу; иначе — текущему | Монолиту через адаптер; адаптер передаёт также F37 и F38, если монолит ищет операции по ним |
| 5 | Если прежний владелец ответил `404 ORIGINAL_NOT_FOUND` (граница по времени, часы терминала) — шлюз повторяет `accept` текущему владельцу с заголовком `X-Lookup-Done` | — |
| 6 | Владелец операции отвечает терминалу через `deliver` в то же соединение | — |

Операции нет и у прежнего владельца — действует правило «исходная не найдена»: реверс
уходит в процессинг по вычисленному `operationId`.

Пересылка работает ограниченное время: окно реверса и срок второй фазы. Когда они истекают,
у монолита не остаётся операций переведённых терминалов, и его можно отключать.
