## Как читать общую схему

- **Толстая линия** — вызов с подтверждением на пути транзакции.
- **Пунктир** — асинхронно: результат процессинга, репликация, настройки.
- **Цифры ①–⑧** — порядок шагов онлайн-транзакции.
- **Знак ◀ в подписи** — обратный путь (шаги ⑥, ⑦, ⑧): данные идут справа налево. Линия без
  стрелки, иначе Mermaid разворачивает схему и терминалы оказываются в середине.
- Все вызовы между сервисами — HTTPS (HTTP/2, mTLS).

## Путь транзакции по шагам

| Шаг | Что происходит | Подтверждение |
|---|---|---|
| ① | Терминал шлёт `0200` по своему постоянному соединению. Маршрутизатор по хешу адресов отдаёт пакеты всегда одному и тому же шлюзу | — |
| ② | Шлюз разбирает сообщение, по номеру терминала (F41) находит блок и передаёт запрос вместе с `sessionId` соединения | `202` от блока |
| ③ | Transaction Receiver проверяет MAC в HSM и записывает транзакцию с ключом идемпотентности | коммит на primary и одной реплике |
| ④ | Processing Sender отправляет операцию в процессинг | `ACCEPTED` — процессинг надёжно принял |
| ⑤ | Процессинг присылает результат позже и по другому соединению | — |
| ⑥ | Callback Router по префиксу `correlationId` находит блок-владелец, Result Receiver записывает итог | наш `200` после коммита |
| ⑦ | Delivery подписывает ответ в HSM и вызывает тот шлюз, чей номер записан в `sessionId` | `DELIVERED` или `NO_SESSION` |
| ⑧ | Шлюз пишет `0210` в соединение терминала | терминал молчит — значит получил; не получил — пришлёт повтор или реверс |

## Сервисы блока

| Сервис | Прежнее имя | Что делает | Что будет, если упадёт |
|---|---|---|---|
| **Transaction Receiver** | Acceptance | Проверяет терминал, MAC и время; вычисляет ключ идемпотентности; записывает транзакцию. На повтор отдаёт сохранённый ответ | Запросы берут соседние поды |
| **Processing Sender** | Dispatcher | Отправляет `Submit`, держит лимит одновременных запросов, отключает процессинг предохранителем при сбоях, выбирает A или B | То же. Незавершённую отправку разберёт Timeout Monitor |
| **Result Receiver** | Result API | Принимает результат процессинга, меняет состояние, отвечает `200` только после коммита | Процессинг повторит результат |
| **Delivery** | — | Подписывает ответ и отдаёт его шлюзу, который держит соединение | Ответ остаётся в БД, терминал заберёт его повтором |
| **Timeout Monitor** | Deadline Worker | Раз в секунду ищет транзакции с истёкшим сроком: спрашивает статус, запускает реверс, закрывает просроченные предавторизации | Работает второй экземпляр; строки не делят благодаря `SKIP LOCKED` |

## Управление и стендины

Терминал закреплён за *логическим* блоком `b5` (кольцо consistent hashing по номеру
терминала). Где этот блок сейчас работает физически — в основном B5 или в стендине SI1 —
записано в карте блоков. При обновлении или аварии меняется одна строка карты. Терминалы не
переподключаются: их соединения держат шлюзы.

Об отказе блока Failover Orchestrator узнаёт сам, без системы мониторинга: опрашивает блок
своими пробами и спрашивает шлюзы и Callback Router, видят ли блок они. Решение принимается,
когда блок не видит большинство наблюдателей.

Управление не стоит на пути транзакции. Если оно недоступно, трафик идёт по последним
полученным настройкам; нельзя только менять маршруты.

## Что нужно терминалу до первой транзакции

| Система | Зачем | Что будет, если недоступна |
|---|---|---|
| DNS | Имя входа → адрес (VIP шлюзов) | В настройках терминала есть запасной список адресов |
| Сервер настроек (TMS) | Адреса входа, таймауты, период эхо, правила переподключения, разрешённые операции | Терминал работает с последними полученными настройками; в прошивке есть значения по умолчанию |
